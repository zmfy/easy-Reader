# TXT 目录整理：快速模式 / 完全 AI 模式 — 设计

日期：2026-11-28　分支：feat/txt-organize（在未合并的整理功能分支上继续）

## 为什么做

完全 AI 整理太慢：《凡人修仙传》5201 条候选行、18 批，每批约 60–70 秒，整本 25–40 分钟；更长的书约 1 小时。
多数人点「让 AI 整理」只是嫌目录乱，等不了半小时。但也有人希望每一行都经过 AI 判断、结果最稳。
所以由发起人自己选：要快用快速模式，要稳用完全 AI 模式，两者区别要写清楚。

## 目标

- 发起整理时可选两种模式，**默认快速**：
  - **快速**：规则先判掉明显的行，AI 只看可疑行。
  - **完全 AI**：现有做法，每条候选行都交给 AI。
- 对话框里写明两者区别，让人能自己判断。
- 进度、审核页能看出这次用的是哪种模式。

## 不做

- 批次并发（以免撞 AI 接口限流；以后另议）。
- 改变候选行挑选、structure、writer、审核采纳等下游逻辑。
- 管理员单独设置「只允许某种模式」。

## 反目标（技术上能跑但算失败）

- 快速模式把真章节判成噪音而删掉（丢正文标题）——规则只能取保守方向：拿不准一律交给 AI。
- 快速模式和完全 AI 模式在同一本书上的目录结构有明显差异（分卷错、章节丢失）。

## 估算依据（《凡人修仙传》原文，脚本粗算）

| | 行数 | 占比 |
|---|---|---|
| 候选行 | 5201 | |
| 规则 1 干净章节 | ≈1750 | 34% |
| 规则 2 孤立编号 | ≈2260 | 43% |
| 剩余交给 AI | ≈1200 | 23%（约 4 批，现为 18 批） |

预计整本从 25–40 分钟降到 7–10 分钟。不同书的比例会不同；孤立编号少的书省得少。

## 做法比较（Approaches）

1. **规则预判 + AI 只判可疑行（采用）**：在候选行与 AI 判定之间加一层规则预标注；快速模式下已预标注的行不发给 AI。改动集中在 judge 一层，下游完全不变。用户已选定。
2. 让 AI 只回报例外（所有行都发，但只返回非 chapter 的）：输入 token 不变，提速有限，且「没回报就是 chapter」放大了漏判风险。不采用。
3. 批次并发：不降低调用量，受限流约束；可与 1 叠加，本次不做。

## 设计

### 规则预标注（新模块，例如 `services/txt-organize/prelabel.ts`）

输入全部候选行，按顺序扫描，维护 `last` = 至今见到的最大「有章名的章号」。

- **规则 1 干净章节 → `chapter`**，同时满足：
  - 行文字匹配「第N章 + 非空章名」（N 为阿拉伯或中文数字，允许前面带「第X卷/第X部」前缀——structure 已能按前缀推断分卷，T4b）；
  - N == last + 1；
  - `bodyChars` ≥ 300；
  - 同样的行文字在前面没有出现过（防止重复章节被当成干净章节）。
- **规则 2 孤立编号 → `noise` / `stray_number`**：
  - 整行只有「第N章」（无章名），且 N ≤ last。
  - 与提示词里 stray_number 的定义一致。
- 不满足的一律不标，留给 AI。
- **`last` 的维护（设计者决定，保守方向）**：
  - `last` 只由「连续链」确定：遇到有章名的第N章，若 N == last + 1 则 last = N；
  - 若 N ≠ last + 1（跳号、回落、错号），**不更新**，记为待确认 N；紧接着的下一个有章名章节若为 N + 1，则认为链已在新位置重建，last = N + 1。这样一个错号（如把「第100章」写成「第1000章」）不会让 last 跳上去，每卷从第一章重新编号的书也能在两章内重新对上。
  - **规则 2 只在链「已建立」时生效**：开头、以及每次遇到卷 / 部行（候选行匹配「第…卷」「第…部」且不带「第N章」）或链断开之后，规则 2 暂停，直到重新出现两个连续的有章名章节。目的：防止「第一卷有章名、第二卷从第一章重新编号且只有编号」的书，把第二卷的真章节当孤立编号删掉。
  - 链断开期间规则 1 同样不生效（N == last + 1 不成立），这些行都交给 AI。
- 中文数字解析复用项目里已有的工具（T3c/T4b 里有章号解析），没有就在模块内实现，覆盖 零〇一二两三…十百千万 与阿拉伯数字；解析失败 = 不标。

### 判定（judge.ts）

- `judgeCandidates` 新增参数 `mode: 'fast' | 'full'`。
- `full`：行为与现在完全一致。
- `fast`：
  - 先跑预标注；可疑行（未标注的）按原有方式分批（每批 300、重叠 20、两次失败对半拆分、网络重试）发给 AI。
  - **规则判掉的行不发给 AI，但每条可疑行多带一个字段 `prevChapter=`：它前面最近一个章节行（规则判定的或前批 AI 判定的）的原文**（设计者决定）。AI 判断孤立编号、重复、错号所依赖的「前一个有名章节」由此得到，输入 token 只增加少量。紧挨着的重复标题本来就在 `prev` 片段里能看到。不采用「把规则行整行作为只读上下文发给 AI」：token 增加多，且要改 parseBatch 的 id 校验。
  - 重叠上文取前面的可疑行。
  - 结构摘要用全部已知标签计算（规则标签 + 之前批次的 AI 标签，截至本批第一条可疑行之前）。
  - 合并结果：规则标签 + AI 标签，仍与候选行一一对应。
  - 现有的结尾校验（至少一个 chapter、第一个有效标签不能是 duplicate）照旧。
  - 可疑行为 0 时不调用 AI，`batches_total` = 0。
  - 追加一条 note：「快速模式：规则判定 X 行，AI 判定 Y 行」。
- 提示词不变（可在快速模式下加一句：「已省略程序判定为正常章节或孤立编号的行，序号不连续是正常的」）。

### 数据与接口

- `txt_organize_jobs` 加列 `mode TEXT NOT NULL DEFAULT 'full'`（已有任务视为完全 AI）。按 db.ts 现有的 ALTER 迁移写法加。
- `POST /reader/:bookId/organize` 请求体可带 `{ "mode": "fast" | "full" }`，**缺省为 `fast`**；非法值 422。已有进行中 / 待审核任务时照旧返回那个任务（不管请求的模式）。
- job 视图（`organizeJobView`）返回 `mode`。
- 每日 3 次的限额两种模式合并计算。
- `docs/api.md` 同步。

### 前端

- Reader 目录里的「目录不对？让 AI 整理」/「重试」按钮：点击后弹出对话框，两项单选，默认选中快速：
  - **快速（推荐）**：程序先判断明显的章节和正文里夹杂的编号，AI 只看拿不准的行。长篇约快 3–4 倍。原书若在某处写错（如重复的章节标题），可能不会被发现。
  - **完全 AI**：每一行都由 AI 判断，结果最稳，长篇可能要半小时以上。
  - 按钮：开始整理 / 取消。
- 进度文字带模式：「正在整理（快速）…（第 2 / 4 批）」。
- 审核页（OrganizedDuplicateCard / ScanBatchReview）显示「整理方式：快速 / 完全 AI」。
- 风格跟随 Reader.vue 现有对话框写法。

### 测试与验证

- prelabel 单测：干净章节、跳号、重复标题、正文过短、卷前缀、孤立编号（≤ / >）、无章名真章节（如「第七十九章」紧接第七十八章 → 不标）、中文数字解析失败。
  - 另需：单个错号不让 last 跳上去；每卷从第一章重新编号（有章名 / 只有编号两种）时不误删；卷行之后规则 2 暂停直到链重建。
- judge 单测：fast 只把可疑行发给 AI（检查 prompt 内容）、标签合并对齐、可疑行为 0 不调用 AI、full 行为不变。
- 路由测试：缺省 mode 为 fast、非法 mode 422、job 返回 mode。
- **真书验证**：《凡人修仙传》用快速模式跑一遍，记录用时和批数，与完全 AI 结果对比目录（基准存于 `.superpowers/sdd/2026-11-27-txt-ai-organize/fanren-full-ai-toc-20261128.txt`，2461 条）。差异需逐条解释；分卷结构须一致。另用《鬼吹灯》（分部 / 分卷、编号不连续）跑一次快速模式，确认没有真章节被删。
